# 阶段 0 笔记：CAN 在线上到底是什么

`lab0.sh` 里的每个结论，都是在这台机器上实测出来的。这份笔记负责把现象背后的
原理补全 —— 只观察不解释，等于只会敲命令。

---

## 1. 一帧的解剖（CAN 2.0A，标准帧）

| 字段 | 位数 | 作用 |
|---|---|---|
| SOF | 1 | 帧起始，一个显性位。所有节点靠它同步 |
| 仲裁场 | 11 + 1 | 11 位 ID + RTR（0=数据帧，1=远程请求帧） |
| 控制场 | 1 + 1 + 4 | IDE（0=标准帧）、r0（保留）、DLC（数据长度） |
| 数据场 | 0 ~ 64 | 经典 CAN 最多 8 字节 = 64 位 |
| CRC | 15 + 1 | 15 位校验 + 1 位界定符 |
| ACK | 1 + 1 | ACK 槽 + 界定符。**任何收到正确帧的节点都要拉低 ACK 槽** |
| EOF | 7 | 帧结束，7 个隐性位 |
| IFS | 3 | 帧间隔，给控制器留处理时间 |

8 字节数据帧合计：

```
1 + (11+1) + (1+1+4) + 64 + (15+1) + (1+1) + 7 + 3 = 111 bit
```

500 kbps 下 = `111 / 500000 ≈ 222 µs`。加上位填充最坏情况约 20 位，约 262 µs。
于是「10 ms 周期发一帧」≈ 2.2% 总线负载。

这个手算比任何工具都可靠，因为工具的估算依赖你告诉它的位速率，而手算只依赖协议本身。

**为什么 ACK 这么重要**：发送方靠「有没有节点拉低 ACK 槽」判断这帧有没有人收到。
总线上只有自己一个节点时，即使物理上完全正常，也会因为没人 ACK 而产生 ACK 错误
并不断重发。这是新手上台架时最常见的困惑。

## 2. DLC 的两个坑

**坑一：DLC 9~15 在经典 CAN 里是合法的。** 值 9~15 都表示「8 字节数据」，
接收方只取前 8 个。所以看到 DLC=12 不代表这是坏帧。

**坑二：CAN FD 的长度编码完全不同。** FD 用 DLC 的 0~15 表示 0~64 字节：

```
0~8  -> 0~8 字节
 9   -> 12 字节      12 -> 24 字节
10   -> 16 字节      13 -> 32 字节
11   -> 20 字节      14 -> 48 字节
                     15 -> 64 字节
```

`lab0.sh` 里发 64 字节 FD 帧，candump 显示 `[64]`，而经典帧显示 `[8]`。
**注意 `[02]` 与 `[2]` 的区别**：FD 帧的显示带前导零，这是 candump 用来
区分 FD 与经典的标记。读日志时靠这个细节就能判断对面发的是 FD 还是经典帧。

## 3. 位定时：vcan 永远给不了你的那部分

`can-calc-bit-timing -b 500000 -s 875 -c 80000000 sja1000` 的输出：

```
 Bitrate TQ[ns] PrS PhS1 PhS2 SJW BRP  ...  SampP  Error   BTR0 BTR1
  500000    125   6    7    2   1  10   ...  87.5%   0.0%   0x09 0x1c
```

逐项拆开：

- **一个 bit 被切成若干 TQ（时间份额）**。TQ = `1 / 时钟 × BRP` = `1/80MHz × 10` = 125 ns。
- 一个 bit 由四段构成：**同步段**(1 TQ) + **传播段 PrS**(6) + **相位缓冲段1 PhS1**(7) + **相位缓冲段2 PhS2**(2) = 16 TQ。
- 16 × 125 ns = 2 µs → 位速率 500 kbps。
- **采样点** = (1+6+7)/16 = 87.5%，即采样发生在 PhS1 与 PhS2 的边界。
- **SJW（重同步跳转宽度）**= 1：允许每个 bit 因时钟误差最多伸缩 1 个 TQ。
  总线上所有节点的晶振不可能完全一致，SJW 就是给这点误差留的余量。
- **BTR0/BTR1** 是 SJA1000 寄存器的实际值，真机上要写进芯片。

采样点为什么常取 87.5%：CAN 总线上一个 bit 的后段最稳定（已经跳变完毕），
采样点越靠后越抗干扰；但太靠后又留给 SJW 的空间不足。CiA 推荐 87.5%。

**vcan 上这些全部没有意义**：虚拟总线不按位传输，一帧就是从用户态内存拷到
另一个套接字的队列。所以 `ip link set vcan0 type can bitrate 500000` 直接返回
`Operation not supported` —— 不是权限问题，是没有控制器。

结论：**vcan 能验证协议、过滤、调度、日志；永远验证不了位定时、仲裁、错误帧。**

## 4. vcan / vxcan / slcan / 真实控制器

| 类型 | 载体 | 能设位速率 | 能产生错误帧 | FD | 典型用途 |
|---|---|---|---|---|---|
| `vcan` | 纯软件（内核模块） | ❌ | ❌ | ✅ | 协议开发、CI 单元测试、教学 |
| `vxcan` | 成对出现，跨 netns 传帧 | ❌ | ❌ | ✅ | 容器 / 网络命名空间隔离测试 |
| `slcan` | 串口 + SLCAN 协议（`slcand`） | ✅（由适配器决定） | 视适配器 | 少见 | 临时接真总线，成本低，带宽受串口限制 |
| 硬件控制器 | SPI / PCI（mcp251x、sja1000、rcar_can…） | ✅ | ✅ | 部分支持 | 生产环境 |

这台机器上 `modinfo vxcan` 不存在（内核没编这个模块），`slcan` 模块在但没有
串口 CAN 适配器，USB 上也没有 CAN 设备 —— 所以只能走 vcan 这一条路。

**关键认知：应用层代码在四种情况下完全一样。** SocketCAN 把差异全部关在驱动里，
`socket(PF_CAN, SOCK_RAW, CAN_RAW)` + `struct can_frame` 这一套与硬件无关。
换真机时改的是 `ip link` 那一行，不是你的 C 代码。

## 5. 错误帧与 Bus-Off：vcan 的盲区

CAN 有五种错误：位错误、填充错误、CRC 错误、格式错误、ACK 错误。

控制器维护两个计数器：

| 计数器 | 何时增加 | 何时减少 |
|---|---|---|
| TEC（发送错误计数） | 发送失败 +8 | 发送成功 -1 |
| REC（接收错误计数） | 接收出错 +1（检测到错误的一方 +8） | 接收成功 -1（满足条件时） |

状态迁移：

```
Error Active  (TEC、REC 都 < 128)   正常收发，出错时发主动错误帧
      ↓ TEC 或 REC ≥ 128
Error Passive (128 ~ 255)           只能发被动错误帧，影响力下降
      ↓ TEC > 255
Bus-Off                             彻底退出总线，收发全停，必须软件恢复
```

**最阴险的是 Bus-Off**：`ip link` 看起来还是 UP，应用 `write()` 也不一定立即报错，
但帧根本发不出去。只能通过 `CAN_RAW_ERR_FILTER` 读错误帧才能发现。
这就是阶段 4 要处理的场景 —— 而 vcan 造不出来，只能靠 `ip link set down`
模拟一个近似的「链路消失」。

## 6. 工具速查（都能在这台机器上直接用）

| 命令 | 用途 | 常用参数 |
|---|---|---|
| `candump` | 抓帧 | `-ta` 时间戳、`-e` 扩展帧标记、`-x` 十六进制、`-l` 写日志、`iface,ID:MASK` 过滤 |
| `cansend` | 发一帧 | `ID#DATA`、`ID#R` RTR、`ID##1DATA` FD+BRS |
| `cangen` | 造随机/周期流量 | `-g` 间隔、`-I` ID、`-L` 长度 |
| `canplayer` | 回放日志 | `-I file`、`-l` 循环、`-t` 变速 |
| `canlogserver` | 网络日志服务 | 多机共享一路总线 |
| `cansniffer` | 只显示**变化**的字节 | 现场调试神器，一眼看出哪个信号在动 |
| `canbusload` | 负载估算 | `iface@bitrate`，列含义见下 |
| `cangw` | 内核态网关/路由 | 阶段 4 用 |
| `canfdtest` | FD 链路自测 | 需要两块真实控制器对接 |

`canbusload` 的列（已实测核对）：`<接口@位速率> <帧/秒> <bit/秒> <载荷bit/秒> <错误> <负载%>`。
验证方法：以 5 帧/秒发 8 字节帧，得到 `5  675  320  0  0%` ——
`675/5 = 135 bit/帧`（111 + 位填充），`5×64 = 320` 载荷位。

## 7. 从阶段 0 到阶段 1 的接缝

阶段 0 里 `candump vcan0,180:7FF` 这个语法，和阶段 2 里 C 代码的

```c
struct can_filter f = { .can_id = 0x180, .can_mask = 0x7FF };
```

是**同一个东西的两层壳**：工具把参数翻译成 `struct can_filter` 再交给内核。
看懂这一层，就知道阶段 2 不是"又学一套新 API"，而是把已经用过的东西写成代码。
