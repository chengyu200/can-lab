# 阶段 6 笔记：UDS（ISO 14229）

## UDS 在诊断栈里的位置

```
  诊断仪 (tester)                           ECU
  ┌──────────────┐                    ┌──────────────┐
  │  UDS 应用    │  10 03 / 22 F1 90  │  UDS 应用    │  ← 阶段 6
  ├──────────────┤ ←────────────────→ ├──────────────┤
  │  ISO-TP      │  FF/CF/FC 分片     │  ISO-TP      │  ← 阶段 5
  ├──────────────┤                    ├──────────────┤
  │  CAN 驱动    │  0x7E0 / 0x7E8     │  CAN 驱动    │  ← 阶段 1-4
  └──────────────┘                    └──────────────┘
```

UDS 只管"请求什么、回什么、允许不允许、错了怎么报"。它不关心报文怎么分片，也不关心跑在 CAN 还是以太网上（DoIP 上跑的是同一套 UDS）。

所以 `uds.c` 是一个纯函数：进一个字节数组，出一个字节数组，一行 socket 代码都没有。这个边界划清楚之后，`ecu_server.c` 里换传输层只需要改 3 个函数。

## 服务清单

| SID | 服务 | 本实现支持 |
|---|---|---|
| `0x10` | DiagnosticSessionControl | 01 默认 / 02 编程 / 03 扩展 |
| `0x11` | ECUReset | 01 硬复位 |
| `0x19` | ReadDTCInformation | 02 按状态掩码读 |
| `0x22` | ReadDataByIdentifier | F190 / F187 / F18C / F191 / 0100 |
| `0x27` | SecurityAccess | 01 请求种子 / 02 发密钥 |
| `0x2E` | WriteDataByIdentifier | F190（VIN） |
| `0x3E` | TesterPresent | 00，支持 suppress 位 |

## 会话与安全的两把锁

| 服务 | 默认会话 | 扩展会话 | 需要解锁 |
|---|---|---|---|
| `0x10` 会话控制 | ✓ | ✓ | — |
| `0x11` 复位 | ✓ | ✓ | — |
| `0x22` 读数据 | ✓ | ✓ | — |
| `0x19` 读 DTC | ✓ | ✓ | — |
| `0x27` 安全访问 | ✓ | ✓ | — |
| `0x2E` 写数据 | ✗ `7F 7E` | ✓ | **✓** |

写操作要过两道关。实测中"只进扩展会话不解锁"和"解锁后复位"两种情况都被正确拦下：

```
未解锁写 VIN      -> 7F 2E 33   securityAccessDenied
复位后写 VIN      -> 7F 2E 22   conditionsNotCorrect
```

## NRC：错误也要分类

| NRC | 含义 | 什么时候用 |
|---|---|---|
| `0x11` | serviceNotSupported | SID 不认识 |
| `0x12` | subFunctionNotSupported | SID 认识，子功能不认识 |
| `0x13` | incorrectMessageLength | 长度不对 |
| `0x22` | conditionsNotCorrect | 会话/状态不满足 |
| `0x24` | requestSequenceError | 没要种子就发 key |
| `0x31` | requestOutOfRange | DID / 参数不存在 |
| `0x33` | securityAccessDenied | 需要解锁 |
| `0x35` | invalidKey | 密钥错 |
| `0x36` | exceedNumberOfAttempts | 错太多次被锁 |
| `0x78` | responsePending | 还在处理，别超时 |

**检查顺序必须固定**：长度 → 会话 → 安全 → 参数。

反过来会有两个问题：长度不对时读不出参数；先报安全错会泄露"这个 DID 存在"。诊断测试用例经常专门验证这个顺序。

## 时序三兄弟

| 参数 | 含义 | 默认 |
|---|---|---|
| P2 | 服务器收到请求到响应的上限 | 50 ms |
| P2* | 回了 `7F xx 78` 之后，延长到这个值 | 5000 ms |
| S3 | 非默认会话下，两次请求的最大间隔 | 5000 ms |

实测响应时间都在 **0～1 ms**，远低于 P2 的 50 ms。这也说明 vxcan 上没有真实总线的排队延迟 —— 真车上 20 ms 的 P2 余量是被总线负载和 ECU 主循环吃掉的。

S3 实测：

```
[用例] 进扩展会话          -> 50 03 00 32 13 88
[等待] 闲置 6000 ms
  ECU: ** S3 超时（5000 ms 无请求），自动退回默认会话 **
[用例] 超时后写 VIN        -> 7F 2E 22   （会话已经掉回默认）
```

S3 的工程意义：诊断仪拔掉之后，ECU 不能一直停在扩展会话里等人。否则任何能发 CAN 帧的设备都能接管诊断通道。

## 完整序列实测

`uds_tester --auto` 跑 15 步，全部通过：

| # | 请求 | 响应 | 说明 |
|---|---|---|---|
| 1 | `10 03` | `50 03 00 32 13 88` | P2=50ms, P2*=5000ms |
| 2 | `22 F1 90` | `62 F1 90` + 17 字节 | VIN = LSVAA123456789012 |
| 3 | `2E F1 90` + VIN | `7F 2E 33` | 未解锁，正确拒绝 |
| 4 | `27 01` | `67 01 18 E6 6E BB` | seed = 0x18E66EBB |
| 5 | `27 02 BD 43 CB 1E` | `67 02` | key = seed ^ 0xA5A5A5A5 |
| 6 | `2E F1 90` + VIN | `6E F1 90` | 解锁后成功 |
| 7 | `22 F1 90` | `62 F1 90` + 新 VIN | 与写入一致 |
| 8 | `19 02 FF` | `59 02 FF` + 3×4 字节 | 3 条 DTC |
| 9 | `22 01 00` | `62 01 00 04 44` | rpm = 1092 |
| 10 | `22 DE AD` | `7F 22 31` | DID 不存在 |
| 11 | `10 03 00 00` | `7F 10 13` | 长度错 |
| 12 | `31` | `7F 31 11` | 服务不支持 |
| 13 | `11 01` | `51 01` | 复位 |
| 14 | `2E F1 90` + VIN | `7F 2E 22` | 复位后会话不对 |
| 15 | `22 F1 90` | `62 F1 90` + VIN | 数据没丢 |

第 14、15 步放在一起看才有意义：复位把会话打回默认（所以写被拒），但 NVM 里的 VIN 还在（所以读得到）。**会话是易失的，数据是持久的**，这两件事在实现里必须分开。

## DTC 与 DID 的编码

DTC 的 3 字节不是 ASCII：

```
byte0 bits7-6 = 系统类别  P=00  C=01  B=10  U=11
byte0 bits5-4 = 第一位数字
byte0 bits3-0 = 第二位数字
byte1         = 第三、四位数字（BCD）
```

所以：

| DTC | 编码 |
|---|---|
| P0301 | `03 01 00` |
| U0100 | `C1 00 00` |
| C1234 | `52 34 00` |

状态字节按位组合，`0x2F` = testFailed + testFailedThisCycle + pending + confirmed + 若干未完成位。

## 一个必须说清楚的边界

阶段 5 的 G 场景证明了：**传输层成功 ≠ 应用层成功**。发送端 `write` 全部返回成功，接收端已经把整条消息丢弃。

UDS 用两个机制补上这个缺口：

1. **正响应 / 负响应**：没有响应就是失败，不靠传输层报告。
2. **P2 超时**：等到 50 ms 还没回，客户端自己重试或报错。

这也是为什么诊断仪不能"发完就走"，必须等响应 —— 它等的不是 CAN 帧，是 ECU 处理完之后的那一句答复。

## 与真实项目的差距

这个实现能跑通整套流程，但离量产还有距离。知道差在哪比假装没有更有用：

1. **NVM 持久化**：VIN、DTC 状态、安全访问计数都该落盘。本实现全在内存里，进程一退就没了。
2. **DTC 状态机**：真实的 DTC 有 operation cycle、aging、healing 一整套规则，不是静态表。
3. **安全算法**：固定异或只能用于教学。真实项目是保密算法 + 随机种子 + 延时锁定 + 尝试计数落盘。
4. **多会话并发**：一个 ECU 可能同时被多个诊断仪访问（产线 + 售后），需要仲裁。
5. **0x78 的真实使用**：擦写 Flash、做长时间自检时才需要，本实现的响应都在 1 ms 内，用不上。
6. **功能寻址**：`0x7DF` 广播给所有 ECU，响应可能冲突，需要处理。

## 复现命令

```sh
cd /root/can-lab && make

# 终端 A：ECU（内核 ISO-TP）
./06-uds/ecu_server -i vxcan1

# 终端 A 换成手写传输层，验证同一套 UDS 逻辑
./06-uds/ecu_server -i vxcan1 --user

# 终端 B：跑完整序列
./06-uds/uds_tester -i vxcan0 --auto

# 验证 S3 超时（要等 6 秒）
./06-uds/uds_tester -i vxcan0 --s3

# 交互模式
./06-uds/uds_tester -i vxcan0
uds> 10 03
uds> 22 F1 90
```
