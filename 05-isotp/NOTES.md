# 阶段 5 笔记：ISO-TP（ISO 15765-2）

## 为什么值得手写一遍

内核 `net/can/isotp.c` 有 1737 行，API 却只有三个调用：`socket` / `bind` / `read`+`write`。中间那 1700 行做的是：分片、等流控、守间隔、校验序号、处理超时、重传策略。

这些逻辑的正确性不容易通过"跑通一次"来验证 —— 20 字节能过，不代表 300 字节能过；300 字节能过，不代表对端不回 FC 时能正确放弃。所以本阶段的做法是：先用 400 行把它写出来，再用故障注入把每一条错误路径都踩一遍，最后才用内核版做对照。

## 四种 PDU

所有 ISO-TP 帧的第一个字节都是 PCI（Protocol Control Information），高 4 位决定类型：

```
 单帧 SF   0x0L  [data 1..7]              L = 长度，最大 7
 首帧 FF   0x1H  0xLL  [6 字节]           长度 = (H << 8) | LL，> 7
 连续帧 CF 0x2N  [7 字节]                 N = 序号 1..15 循环
 流控帧 FC 0x3S  0xBS  0xSTmin            S = 0 继续 / 1 等待 / 2 溢出
```

实测（`lab5.sh` E5.2，20 字节）：

```
300  [8]  10 14 11 22 33 44 55 66      首帧：长度 0x014 = 20
308  [3]  30 00 00                     流控：继续，BS=0，STmin=0
300  [8]  21 77 88 99 00 AA BB CC      连续帧 1
300  [8]  22 DD EE FF 11 22 33 44      连续帧 2
```

`6 + 7 + 7 = 20`，正好。

## 三个一定会踩的坑

### ① 首帧不一定是 `10` 开头

300 字节的实测首帧是 `11 2C`。因为 300 = 0x12C，超过 255 时长度的高 4 位要占用 PCI 的低 4 位。

```c
b[0] = 0x10 | ((len >> 8) & 0x0F);   // len=300 时得到 0x11
b[1] = len & 0xFF;                   // 0x2C
```

写死 `if (data[0] == 0x10)` 判断首帧的代码，在小于 256 字节时全部正常，一旦超过就失效。这种"小包正常、大包必挂"的现象，在真车上很难定位。

### ② 序号 15 之后回到 1，不是 0

```c
seq = (seq % 15) + 1;    // 1..15,1..15,...
```

300 字节的 42 个连续帧，序号序列实测：

```
123456789ABCDEF0123456789ABCDEF0123456789A
```

如果写成 `seq = (seq + 1) % 16`，会得到 `1..15,0,1..`，接收端在第 16 帧判错，现象同样是"小包正常、大包必挂"。

### ③ BS 是双向约定，忘了续发就把对端卡死

BS（Block Size）表示"你可以连发几帧，然后停下来等我"。**接收端在一个 block 收满后必须再发一个 FC**，否则发送端会一直等下去。

这个坑是我在写 `isotp_fault.c` 时踩到的：第一版只在收到首帧时回了一次 FC，结果 BS=2、100 字节的场景直接卡到 `N_Bs` 超时。补上续发之后：

```
[CF 1] seq=1 收到 7 字节，累计 13/100
[CF 2] seq=2 收到 7 字节，累计 20/100
     （收满 2 帧，续发流控）
  -> 回 FC：fs=0  bs=2  stmin=0x00
```

100 字节 = 14 个 CF，BS=2 时正好 7 次 FC。

## 定时参数

| 参数 | 含义 | 本实现取值 |
|---|---|---|
| `N_Bs` | 发送端等 FC 的超时 | 1000 ms |
| `N_Cr` | 接收端等下一个 CF 的超时 | 1000 ms |
| `N_As` | 单帧发送完成的超时 | 未实现（依赖驱动） |
| `N_WFTmax` | 最多容忍几个 WAIT | 无限 |

`N_Cr` 容易被忽略：一条 4000 字节的消息总超时可能给 5 秒，但如果对端发到一半死掉，不该让我们干等 5 秒。所以 `isotp_recv` 里对"帧间等待"单独设了 1 秒上限。

## 故障注入实测

`t_stage5.sh` 跑七轮，每轮换一种坏接收端。这些都是实测输出：

| 场景 | 发送端行为 | 耗时 |
|---|---|---|
| 正常对端 | 成功 | 0.3 ms |
| 不回 FC | `ETIMEDOUT`，发完 1 帧就停 | **1001 ms** |
| 回 OVFLW | 立即中止，`ENOBUFS` | 0.2 ms |
| 先回 3 次 WAIT | 继续等，最终成功（RX 4 帧） | 0.3 ms |
| BS=2 | 每 2 帧停一次，共 7 次 FC | 0.6 ms |
| STmin=100 ms | 遵守 100 ms 帧间隔 | **100.6 ms** |
| **CF 序号错乱** | **发送端仍然报告成功** | 0.3 ms |

最后一行是整个阶段最重要的一条：

```
[CF 2] seq=2 收到 7 字节，累计 20/100
     （故意错序，等下一帧触发校验失败）
[CF 3] 序号 3 与期望 4 不符 —— 丢帧了，整条消息作废
```

接收端已经整条丢弃，发送端却因为 `write` 全部返回成功而报告 PASS。CAN 没有传输层 ACK，**"发出去了"和"对方收到了"是两件事**。

这正是 UDS 需要应用层响应 + P2 超时的根本原因，也是阶段 6 的前提。

## 与内核实现的对照

| | 用户态版 | 内核版 |
|---|---|---|
| 协议逻辑代码 | 约 400 行 | 0（调用方） |
| 内核实现 | — | `net/can/isotp.c` 1737 行 |
| 打开方式 | `socket(PF_CAN, SOCK_RAW)` | `socket(PF_CAN, SOCK_DGRAM, CAN_ISOTP)` |
| 写 | 自己拼 FF/CF | `write(fd, buf, len)` 一次写完 |
| 读 | 自己组包 | `read()` 直接拿到完整消息 |
| 流控参数 | 自己解析 FC | `CAN_ISOTP_RECV_FC` 选项 |

调用方的差别只有大约 20 行 —— 但少了这 20 行，就不知道 `1001 ms` 这个超时是从哪来的。

### 一个 API 顺序陷阱

`CAN_ISOTP_RECV_FC` 必须在 `bind()` **之前**设置：

```c
s = socket(PF_CAN, SOCK_DGRAM, CAN_ISOTP);
setsockopt(s, SOL_CAN_ISOTP, CAN_ISOTP_RECV_FC, &fco, sizeof fco);  // 先
bind(s, ...);                                                       // 后
```

反过来会返回 `EISCONN`（Transport endpoint is already connected）。因为 `bind` 之后 ISO-TP 连接就已经建立了。

## 互操作验证

两个实现在字节层面符合同一份标准，所以应该能互相收发。`t_kernel.sh` 跑了四个方向：

| 方向 | 长度 | 结果 |
|---|---|---|
| 用户态发 → 内核收 | 100 | 通过，和校验一致 |
| 内核发 → 用户态收 | 100 | 通过，14 个 CF 序号连续 |
| 内核发 → 内核收 | 4000 | 通过，`write` 返回 4000 |
| 内核收端 BS=2 STmin=50 → 用户态发 | 100 | **684 ms**，14 帧 × 50 ms ≈ 700 ms |

最后一行说明用户态发送端确实在读内核给的 FC 参数，而不是按自己的节奏硬发。

## 没有实现的部分

保持简单是有意的，但要知道边界在哪：

1. **CAN FD**：FD 下单帧可到 62 字节，首帧可带 30 字节，连续帧 63 字节。改动点集中在 `n6 = 6` / `n7 = 7` 这两处和 DLC 编码上。
2. **扩展寻址**：PCI 前面多一个地址字节，用于同一 CAN ID 上区分多个逻辑连接。
3. **多连接并发**：现在的 `isotp_chan` 是单连接阻塞式。真实 ECU 往往同时服务多个诊断连接，需要事件驱动 + 连接表。
4. **重传**：ISO-TP 标准本身不定义重传，由上层（UDS 的 P2 超时）决定。
