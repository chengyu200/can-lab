# 阶段 7：J1939 —— 地址、PGN、传输协议

J1939 是商用车（卡车、客车、工程机械）的上层协议。它和前面几个阶段最大的区别是：
**它在 CAN 之上定义了一整套"谁在说话、说的是什么、说给谁"的结构**，
而不是像 ISO-TP 那样只解决"怎么把长消息拆开"。

如果你只记一件事，记这个：**J1939 的 29 位 ID 是一个结构体，不是一个数值。**

```
   28      26 25 24 23      16 15       8 7        0
   +---------+--+--+----------+-----------+----------+
   | Priority|R |DP|    PF    |    PS     |    SA    |
   +---------+--+--+----------+-----------+----------+
       3bit  1  1     8           8           8
```

## 一、地址声明：J1939 的地基

经典 CAN 没有源地址，收到一帧不知道是谁发的。J1939 把最低 8 位固定为 SA（源地址），
于是每个 ECU 上电第一件事是抢一个地址。

抢的方式是广播一帧 PGN `0xEE00`，数据就是 8 字节 NAME（64 位，出厂唯一）。实测：

```
$ ./07-j1939/j1939_addr vxcan1 0x80 0x1000
  声明帧 ID 应为 0x18EEFF80  (prio=6 PF=0xEE PS=0xFF SA=0x80)

 (1794064143.784611)  vxcan0  18EEFF80   [8]  00 10 00 00 00 00 00 00
```

`18EEFF80` 是算出来的，不是猜的：优先级 6、PF=0xEE、PS=0xFF（广播）、SA=0x80。
数据 `00 10 00 ...` 是 NAME `0x1000` 的**小端**字节序 —— 用 hex 打印会反过来，
看 candump 时极易读错，所以程序里专门按"总线字节顺序"打印了一遍。

### 仲裁：NAME 小的赢，输的一方发不出任何业务报文

两个 ECU 都想要 `0x80` 时，比较 NAME，数值小的赢。内核里就是一行：

```c
if (ecu->name > prev->name)      // net/can/j1939/address-claim.c
        j1939_ecu_unmap_locked(ecu);   // 名字大的出局
```

实测（A 用 NAME=0x2000，B 用 NAME=0x1000，都申请 0x80）：

```
节点 A（NAME=0x2000）：
  -> 争用 0x80：本机 NAME 更大，**本机输**，应改用其他地址
[TX  2] 发送 EEC1 失败: Cannot assign requested address (errno=99)

节点 B（NAME=0x1000）：
  -> 争用 0x80：本机 NAME 更小，**本机赢**，对方应换地址
```

**这一点和直觉不同**：输掉仲裁不是"继续发但对方忽略"，而是内核直接把该 NAME 的
地址映射摘掉，之后它的 `sendto` 返回 `EADDRNOTAVAIL`。原因是内核发送前会
用 NAME 反查地址（`j1939_ac_fixup`），查不到有效单播地址就丢包。

而**接收完全不受影响** —— A 输掉地址后仍在收 B 的帧：

```
[RX] PGN=0x0F004(EEC1) SA=0x80 DA=0xFF len=8  00 91 8C 00 19 00 00 00
```

这符合物理直觉：丢掉地址只是"不能再说话"，耳朵还在。

### 两个内核不会替你做、文档也很少提的事

1. **`bind()` 不会广播地址声明。** 绑定只是在内核里登记"我这个 NAME 想用这个地址"，
   真正的声明帧要应用层自己发。所以只 `bind` 不 `claim` 的节点，别人根本不知道它存在。

2. **内核不应答"请求地址声明"（PGN 0xEA00）。** 规范要求任何 ECU 收到这个请求都要
   重播自己的声明，但内核没有实现。这意味着：**如果没人应答，新上线的节点会以为总线上只有自己。**
   本阶段的 `j1939_addr` 用 4 行代码补上了这个义务：

   ```c
   if (req == PGN_ADDRESS_CLAIM)
           j1939_claim(s, name);
   ```

   这类"协议要求、内核不管"的空档，是实际项目里最容易出问题的地方。

## 二、PDU1 与 PDU2：一个 PF 决定两件事

`PF < 0xF0` 是 PDU1（点对点），`PF >= 0xF0` 是 PDU2（广播）。差别在于 PS 的身份：

| | PF | PS 是什么 | PGN 里含 PS 吗 |
|---|---|---|---|
| PDU1 | < 0xF0 | 目标地址 DA | 不含（记 0） |
| PDU2 | >= 0xF0 | 组扩展 GE | 含 |

同一份发送代码，只改 `--pgn` 和 `--dest`，实测出两种 ID：

```
 (1794064152.728081)  vxcan0  18EA9080   [3]  00 01 02          <- Request, DA=0x90
 (1794064153.283863)  vxcan0  18F00480   [8]  00 01 02 00 19... <- EEC1, 广播
```

- `18EA9080`：PS=`0x90` 是**目标地址**，PGN 仍是 `0xEA00`。
- `18F00480`：PS=`0x04` 是**组扩展**，和 PF=`0xF0` 一起构成 PGN `0xF004`。

这就是为什么 PGN 不能用"ID 的低 18 位"直接算 —— PDU1 时 PS 是地址，
发给 0x90 和发给 0x91 的同一个 PGN 会得到两个不同的低 18 位。

## 三、传输协议：BAM 与 RTS/CTS

超过 8 字节就要分片。**用哪种方式由目标地址自动决定**，不需要额外参数 ——
这是 J1939 和 ISO-TP 设计哲学上最直观的差别：

### 广播 → BAM

```
 (1794064156.099922)  vxcan0  18ECFF80   [8]  20 14 00 03 FF F1 FE 00
                              ^^ BAM  ^^^^^ 20 字节  ^^^^^ 3 包  ^^ 广播
 (1794064156.157902)  vxcan0  18EBFF80   [8]  01 ...
 (1794064156.217911)  vxcan0  18EBFF80   [8]  02 ...
 (1794064156.277920)  vxcan0  18EBFF80   [8]  03 ...
```

数据帧间隔实测 **58.0 ms / 60.0 ms**（规范是固定 50 ms，看下面关于这台机器的说明）。

BAM 是"喊话"：不等任何人回应、不重传、丢了自己负责。

### 单播 → RTS/CTS

```
 (1794064159.025770)  vxcan0  18EC9080   [8]  10 14 00 03 03 F1 FE 00   RTS，我能发 3 包
 (1794064159.025863)  vxcan0  18EC8090   [8]  11 03 01 FF FF F1 FE 00   CTS，你发 3 包，从 1 号开始
 (1794064159.025917)  vxcan0  18EB9080   [8]  01 ...
 (1794064159.025917)  vxcan0  18EB9080   [8]  02 ...
 (1794064159.025917)  vxcan0  18EB9080   [8]  03 ...
 (1794064159.025983)  vxcan0  18EC8090   [8]  13 14 00 03 FF F1 FE 00   EOMA，收完了
```

数据帧间隔 **0.0 ms** —— 因为 CTS 一次授权了 3 包，发方不必等。

| | BAM | RTS/CTS |
|---|---|---|
| 目标 | 广播 | 单播 |
| 是否协商 | 否 | 是（RTS → CTS） |
| 包间隔 | 固定 50 ms | 受 CTS 窗口约束，窗口内连续发 |
| 丢包处理 | 无法感知 | 可用 CTS 重发指定序号 |
| 结束标志 | 无 | EOMA |

### 和 ISO-TP 对照

| | ISO-TP（阶段 5） | J1939 TP |
|---|---|---|
| 首帧 | `FF`，PCI 高 4 位 = 1，低 4 位带长度 | `RTS`（TP.CM，独立 PGN `0xEC00`） |
| 流控 | `FC`，`BS` + `STmin` | `CTS`，窗口 + 下一个序号 |
| 数据帧 | `CF`，PCI 低 4 位是序号 | `DT`（TP.DT `0xEB00`），首字节是序号 |
| 广播 | `CF_BROADCAST` 选项 | `BAM`，无流控、固定 50 ms |
| 地址 | CAN ID 本身就是"地址" | 29 位 ID 里的 SA/DA + 动态地址声明 |
| 最大长度 | 受 FF 的 12 位长度限制（4095） | 1785 字节（255 × 7） |

两套协议解决同一个问题，但 J1939 把传输层做成了**独立的 PGN**，
所以它在总线上是可见、可抓、可被第三方解析的；ISO-TP 把控制信息塞在 PCI 里，
更紧凑但也更"隐形"。

## 四、这台机器上的测量偏差（必须说明）

规范写的是 BAM 固定 50 ms 间隔，实测 58 和 60 ms。原因与阶段 4 相同：
这台 QEMU 没有 KVM（`dmesg` 里 `HYP mode not available`），定时器只能到毫秒级，
`j1939_tp_schedule_txtimer(session, 50)` 的实际触发被推迟。

**但结论不受影响**：BAM 是"按固定间隔一个包一个包发"，RTS/CTS 是"授权多少就连发多少"，
这个本质差异用 0.0 ms vs 58 ms 的对比已经足够说明。真机上 BAM 会稳定在 50 ms 附近。

## 五、一个容易误判的点：`sendto` 的返回值

`j1939_node` 发送 20 字节时报"耗时 0 ms"，看起来像没发出去。实际上：

**`sendto` 只是把消息交给内核的 TP 会话，真正的分片和发送在后台定时器里进行。**
所以它立刻返回，返回成功也只代表"排队成功"。

要知道"到底发完没有"，得用 `SO_J1939_ERRQUEUE` 配合 `SO_TIMESTAMPING` 读错误队列，
内核会在 TX_ACK / TX_ABORT 时投递通知。这是 J1939 里做可靠性传输的标准做法，
也是和阶段 5 那个"发送端报成功、接收端已丢弃"的坑同一个根源：
**CAN 没有传输层 ACK，"交出去"和"送到了"是两件事。**

## 六、复现

```sh
cd /root/can-lab && make

./07-j1939/lab7.sh                 # 四个实验一次跑完
./07-j1939/j1939_addr vxcan0 0x80 0x2000 --claim-period 1000   # 终端 A
./07-j1939/j1939_addr vxcan1 0x80 0x1000 --claim-period 1000   # 终端 B

./07-j1939/j1939_node vxcan0 0x90 0x3000 --rx-only             # 接收端
./07-j1939/j1939_node vxcan1 0x80 0x1000 --pgn 0xFEF1 \
        --dest 0xFF --size 20 --period 0 --count 1             # BAM
./07-j1939/j1939_node vxcan1 0x80 0x1000 --pgn 0xFEF1 \
        --dest 0x90 --size 20 --period 0 --count 1             # RTS/CTS
```
