# 阶段 3 笔记：从「收发字节」到「设计一条总线协议」

阶段 1、2 解决的是「怎么发、怎么收、怎么过滤」。阶段 3 换了个问题：
**两个节点之间要交换什么，用什么格式，多久一次，对方不说话怎么办。**

这一层是车载网络真正的难点。CAN 本身只提供 8 字节的广播信封，
里面装什么、谁先发、丢了怎么办，全靠协议设计。

---

## 1. 报文怎么切分

本实验台的三条报文按「变化速度 + 用途」切：

| 报文 | 周期 | 为什么是这个周期 |
|---|---|---|
| 0x180 ENGINE_FAST | 10 ms | 转速是闭环控制量，人要能感觉到抖动，10ms（100Hz）是动力总成的常见档位 |
| 0x181 ENGINE_SLOW | 100 ms | 水温、油压是热惯性量，时间常数以秒计，10Hz 已经过分充足 |
| 0x200 DASH_CMD | 事件 | 命令不该周期性重发，否则总线上全是重复决策 |

**切分原则**：把时间常数差一个数量级以上的信号分开。合在一条报文里，
只能按最快的那个周期发，慢变量就白占 90% 的带宽。

反过来，如果两个信号必须**同时有效**（比如力矩请求和它的使能位），
就必须放在同一帧里 —— 分成两帧就一定会出现「新力矩配旧使能」的中间态。

## 2. 信号在 8 字节里怎么摆

三条规则：

1. **小端（Intel）优先**。ARM/x86 上最自然，`can_bits_get()` 那种逐位拼装对
   任意 start/len 都成立，不依赖编译器的位域布局。大端（Motorola）在 DBC 里是
   `@0`，位序定义反直觉，容易算错，除非对接的既有项目要求，否则不主动用。
2. **留有保留位**。0x180 只用掉 5 个字节，剩下 3 字节全 0。将来加信号不用改 DLC，
   老接收端也不会因为长度变化而拒绝。
3. **一定要有计数器**。原因见第 5 节。

`factor/offset` 不是花活。发动机控制器内部是 16 位 ADC 原始值，
应用层只关心 rpm。用 `0.25 rpm/bit` 把两者分开：

```c
物理值 = 原始值 × factor + offset
```

好处是换一款分辨率更高的控制器时只改表里的 factor，上层代码一行不动。
代价是要注意**量化误差**：0.25 rpm/bit 意味着 1000.0 和 1000.2 在总线上是同一个值。

`offset` 的典型用法是温度：8 位无符号存 -40..215°C，`offset = -40`。
零下温度在车上很常见，不能假设都是正数。

## 3. 周期发送：三种写法，只有一种能用

```c
/* ✗ 最差：处理耗时累加进周期，越跑越慢 */
while (1) {
    send();
    usleep(10000);
}

/* ✗ 好一点，但仍会把本次处理耗时算进去 */
while (1) {
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    send();
    clock_gettime(CLOCK_MONOTONIC, &t1);
    sleep_remaining(10000 - elapsed(t0, t1));
}

/* ✓ 绝对时间：睡到「某个时刻」，误差不累积 */
struct timespec next;
clock_gettime(CLOCK_MONOTONIC, &next);
while (1) {
    add_ms(&next, 10);
    clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL);
    send();
}
```

**抖动（jitter）和漂移（drift）是两件事**：

- 漂移 = 平均周期偏离标称值，会累积。相对延时写法必然漂移。
- 抖动 = 单次周期的偏差，不累积。绝对时间写法漂移为 0，但抖动仍然存在
  （取决于调度器什么时候把 CPU 给你）。

绝对时间写法的副作用是「补帧」：某一拍被延迟 5ms，下一拍只剩 5ms 就要发，
于是两帧挤在一起。这在总线上表现为瞬时负载翻倍，比均匀抖动更值得警惕。
如果下游有严格的间隔要求，就得改用 BCM（阶段 4），由内核定时器发。

## 4. 超时监控：沉默也是一种故障

节点掉线时总线不会报错，只是安静下来。以下几种写法都发现不了：

```c
recv(s, &f, sizeof f, 0);          /* ✗ 永远阻塞，节点死了就永远等 */
while (poll(&pfd, 1, -1) > 0) ...   /* ✗ 同上，无限超时 */
```

正确做法是给 `poll` 一个远小于判据的超时，然后单独检查「上次收到是什么时候」：

```c
poll(&pfd, 1, 50);                 /* 50ms 醒一次 */
if (have_fast && now - last_fast > 100ms) → 判失效
```

判据取多少个周期？工程上常见 3 个：1 个周期太敏感（一次调度延迟就误报），
10 个周期太迟钝（人已经感觉到异常了）。本实验台用 100ms / 10ms = 10 个周期，
偏保守，是为了在这台抖动很大的虚拟机上少误报。

另外两个细节：

- **失效后要冻结显示，而不是继续显示旧值**。仪表盘上「上个周期的转速」
  比「------」危险得多，因为人看不出来它已经不动了。
- **失效期间不要做控制决策**。`control()` 第一行就是 `if (fast_stale) return;`
  数据不可信时发命令，等于闭着眼睛开车。

## 5. 丢帧检测：间隔法为什么不行

第一版用到达间隔估丢帧：

```c
if (gap > 1.5 * period)
    lost += gap / period - 1;      /* ✗ 把延迟当成丢帧 */
```

实测立刻暴露问题：发送端 26 秒发了 2600 帧，接收端收了 2600 帧，
零丢失，但仪表报了「丢 9 帧」。因为这台虚拟机的调度延迟经常达到 20~30ms，
一个 30ms 的间隔被算成了「丢了 2 帧」。

**延迟和丢失在接收端看来完全一样**，除非协议自己提供依据。
所以 0x180 的 bit32 放了滚动计数器：

```c
delta = (seq - last_seq) & 0xFF;    /* 回绕自动正确 */
if (delta == 0)        → 重复帧
else if (delta < 128)  → 丢了 delta-1 帧
else                   → 计数器回退，节点重启
```

（`delta >= 128` 判为重启，是因为正常丢帧不会一次丢 128 帧 —— 那已经是
节点消失几秒钟了，早就被超时监控抓走了。）

这一字节就是 AUTOSAR E2E Profile 1 里 counter 字段的最小版本。
真实的 E2E 还带 CRC：

```
| counter(4bit) | data id(16bit) | CRC(8bit) | 信号... |
```

CRC 防的是「数据被篡改/位翻转」，counter 防的是「帧丢失/重复/乱序」。
车上凡是安全相关的报文（转向、制动、扭矩）都必须带这两样。

**丢失和卡顿要分开统计**：计数器跳号 = 真丢帧（发送端没发出来，或驱动丢了）；
计数器连续但间隔大 = 卡顿（发了，在路上耽搁了）。前者要查发送端，
后者要查调度/总线负载，是完全不同的两个排查方向。

## 6. 闭环控制里的两个小习惯

`ecu_dash` 只做了一件事：转速过高就让发动机降扭。但有两个细节值得抄走：

**迟滞（hysteresis）**：3000 触发、2600 解除。如果只用 3000 一个阈值，
转速在 3000 附近抖动时会疯狂发命令，把总线打满。

**命令节流**：两条命令之间至少隔 4 秒。即使逻辑上判断该发，也不发 ——
防止上游异常时把总线刷爆。这个「最小间隔」在真实 ECU 里几乎必然存在。

## 7. 这套东西往后怎么长

- **诊断（UDS/ISO-TP）**：0x300/0x308 是预留的。真做起来要处理
  单帧/首帧/连续帧/流控帧的分片，以及 P2/P2* 超时。这台机器的内核没有
  `can_isotp` 模块，得在用户态实现。
- **网络管理（NM）**：节点该什么时候睡、什么时候醒，靠周期性的 NM 报文协调。
  本质上是「用一条报文的超时判断整条总线该不该休眠」，和本阶段的超时监控同一套逻辑。
- **网关**：多个 CAN 网段之间的报文转发与过滤，内核的 `can_gw`（cangw 命令）就是干这个的。
