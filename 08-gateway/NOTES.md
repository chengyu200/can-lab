# 阶段 8：双段网关 —— 协议转换、断链、记账

前面七个阶段都是"一条总线上的节点"。真实车上不是这样：动力总成、车身、信息娱乐
各自一条总线，速率和协议都不同，中间靠网关转接。

```
[engine]---vxcan0 ~~ vxcan1---[gw]---vxcan2 ~~ vxcan3---[J1939 接收端]
            A 段 私有 CAN               B 段 J1939
```

`vxcan` 是点对点的（一端发只有对端收），所以两段总线需要两对 vxcan，
中间由 `gw` 桥接 —— 这恰好就是网关在车上的物理位置。

## 一、网关的核心不是"转发"，是"翻译"

`gw.c` 里有三种动作，从简单到复杂：

| 动作 | 干什么 | 例子 |
|---|---|---|
| `FWD_COPY` | 原样转发 | `0x200` 从 B 段回到 A 段 |
| `FWD_REMAP` | 转发但换 ID | `0x181` → `0x281` |
| `FWD_EEC1` | 解信号、按另一套量纲重编码 | `0x180` → J1939 `0xF004` |

第三种才是真正的网关工作。实测的转换明细（`--trace 6`）：

```
[vxcan1->vxcan2] 0x180 A4 0E 2E 15 29 00 00 00  ->  0x18F00400 00 8F 92 48 1D 00 00 00   rpm 937.0 -> 937.0
                 ^^^^^ ^^^^^ ^^ ^^ ^^                ^^^^^^^^^^    ^^ ^^ ^^^^^ ^^
                 ID    rpm   thr load alive          EEC1 ID       扭矩 扭矩 转速
```

算一遍：

- A 段：`A4 0E` 小端 = `0x0EA4` = 3748，乘 0.25 = **937.0 rpm**
- B 段：`48 1D` 小端 = `0x1D48` = 7496，乘 0.125 = **937.0 rpm**

**原始值正好差一倍，物理值相等。** 这就是量纲陷阱：如果图省事把 8 个字节直接搬过去，
B 段会解出 1874 rpm —— 一个"看起来有数、但完全错误"的值。这类 bug 在车上极难查，
因为数值不是 0 也不是溢出，只是默默地翻了一倍。

扭矩的偏移量也变了：A 段的 `load` 是 0..100 的百分比，EEC1 是 1%/bit 且**偏移 -125**
（范围 -125..125%）。所以 `load=22` 要编码成 `22+125=147=0x93`。实测里 `0x92/0x93`
正是这个偏移后的值。

## 二、断链有两种形态，处理方式完全不同

这一点值得单独说，因为很容易混淆：

| 形态 | 现象 | 正确做法 | 前面哪个阶段 |
|---|---|---|---|
| 接口被**删除** | `ifindex` 失效，socket 绑定的索引指向空气 | 重新 `bind`（按接口名重查索引） | 阶段 4 `link_watch` |
| 接口**down 掉** | `write` 返回 `ENETDOWN`，socket 本身有效 | 继续收，等着恢复，**不要重建 socket** | 本阶段 |

车上绝大多数故障是第二种：ECU 掉电、线束断开、收发器进休眠。总线还在、接口还在，
只是对面没人。实测：

```
$ ip link set vxcan2 down
[-] vxcan2 段不可用（Network is down），暂停转发，继续接收

$ ip link set vxcan2 up
[+] vxcan2 段恢复，开始转发
```

网关全程没有退出、没有重建 socket，A 段的接收一秒都没停。**这是网关必须做到的事**：
它一侧的故障不能影响另一侧。

注意日志里 `[-]` 只打了一次而不是几万次 —— 用 `up` 状态位做边沿检测。
每帧打一条日志会在 10 ms 周期下把磁盘写满，这是嵌入式日志的经典事故。

## 三、记账：为什么这里不用内核过滤器

阶段 2 学过 `CAN_RAW_FILTER`，让内核先丢，省 CPU。但网关**故意没用**：

内核丢掉的帧，用户态永远看不见，于是"我丢了多少"这个问题就没有答案了。
而网关的价值恰恰在于能说清楚每一帧的去向 —— 现场排查"仪表为什么不显示"时，
第一个要问的就是"网关转了吗、丢在哪一段"。

代价是 CPU：所有帧都要进用户态。量产网关的折中是硬件过滤 + 硬件计数寄存器，
既省 CPU 又能记账。这里选可观测性，是因为教学场景下"看得见"更重要。

实测最终账目：

```
  A段 vxcan1   rx=1608   tx_ok=1      tx_err=0    状态=UP
  B段 vxcan2   rx=2      tx_ok=1166   tx_err=443  状态=UP
  规则 0x180 ENGINE_FAST -> J1939 EEC1 (0xF004)       进 1462   出 1060
  规则 0x181 ENGINE_SLOW -> 0x281 透传（ID 重映射） 进 146   出 106
  规则 0x200 DASH_CMD -> 原样回 A 段              进 1      出 1
```

`1462 - 1060 = 402`，`146 - 106 = 40`，合计 442 帧，正好是 4 秒断链期间
A 段 10 ms + 100 ms 两个周期的产量（400 + 40）。

**这个数字本身就是结论**：网关是单点，它一侧断 4 秒，就有 442 帧数据永远消失。
所以真实网关必须回答"断了之后怎么办"：

- 丢最新的（当前做法，简单）
- 丢最旧的（保实时性）
- 按优先级丢（保安全相关信号）
- 缓存等恢复（保完整性，但要有容量上限和过期策略）

## 四、真实网关还缺什么

这个程序刻意停在了"能跑通、能说清楚"的程度。往产品化还差这些：

1. **速率限制与优先级映射。** A 段 10 ms 的报文搬到 100 ms 周期的 B 段，
   带宽需求变了。不限制的话，一个高频段能把低速段灌满，丢的反而是安全报文。

2. **TP 报文不能盲目透传。** 这是最容易踩的坑：网关的 raw socket 看到的是
   `TP.CM` / `TP.DT` 这些**分片帧**，不是重组后的消息。如果直接把 29 位帧转发到另一段，
   而另一段的 SA 被重映射过、或者 MTU/波特率不同，接收端会因为"序号对不上/超时"而整条丢弃。
   正确做法是：在这一段用 J1939 socket 重组，再在另一段重新分片。
   （本阶段的 `FWD_COPY` 只处理 8 字节以内的单帧，正是为了不碰这个问题。）

3. **睡眠与唤醒。** 车上网关要管整条网络的休眠，一条 "keep alive" 报文能让所有节点不睡。

4. **故障降级。** B 段长时间不恢复时，网关应该给 A 段回一个"该信号无效"的替代值，
   而不是让仪表一直显示最后一帧 —— 那是比空白更危险的显示。

## 五、复现

```sh
cd /root/can-lab && make

./08-gateway/topo.sh up|down|status|reset    # 建/拆两段总线
./08-gateway/lab8.sh                         # 全流程演示（约 20 秒）
```

手动分开跑：

```sh
./03-app/ecu_engine vxcan0                                   # A 段：发动机
./08-gateway/gw vxcan1 vxcan2 --stats 3 --trace 5            # 网关
./07-j1939/j1939_node vxcan3 0x90 0x3000 --rx-only           # B 段：J1939 接收

ip link set vxcan2 down      # 制造断链
ip link set vxcan2 up        # 恢复
cansend vxcan3 200#010A      # 反方向：B 段命令回 A 段
```
